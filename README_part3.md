## 3. Обоснование весов композиции

Раньше веса были одним хардкод-словарём (`regression: 0.5, worldpop: 0.3,
distance_to_city: 0.1, distance_to_center: 0.1`) без обоснования и без
учёта 5 новых масок.

**Методология** (`src/masks/weighting.py`, `resolve_weights()`):

1. Вес `regression` = r2 калибровки показателя (прямая эмпирическая мера
   объяснённой дисперсии) — не константа.
2. Остаток бюджета (1 − r2) делится между "общими" масками-прокси
   (worldpop, distance_to_city, distance_to_center — участвуют всегда) и
   "промышленными" (territory, road_network, railway, road_traveltime,
   power — только для показателей `category: industrial`).
3. Приоры внутри каждой группы и доля бюджета под промышленные маски
   (`industrial_budget_share`) — в `src/masks/config.yaml`, с обоснованием
   в комментариях, а не в коде.

**Новые файлы:**

- `src/masks/weighting.py`

**Изменённые файлы:**

- `src/masks/config.yaml` — структура `composition.proxy_priors` /
  `industrial_priors` / `industrial_budget_share` вместо плоского
  `default_weights`; у `indicators` добавлено поле `category`

**API:** `GET /api/default-weights?indicator=<code>` (`apps/api/main.py`) —

**Фронт:** `App.jsx` — пресет "Автоподбор (по показателю)" заменил бывший

## 4. Пики на суммарном слое

Пики считаются в SQL живого пути: `percentile_cont(0.95)` в `_AGG_SQL`
(`main.py`), порог возвращается как `RecomputeResult.peak_threshold` —
фронт сравнивает `["get","value"] >= peak_threshold` MapLibre-выражением,
не считает пики сам.

Порог перцентиля — только по **ненулевым** ячейкам: в разреженном регионе,
где нулей больше (1 − N%), перцентиль по всем ячейкам схлопывается в 0, и
"пиком" становится любая ненулевая ячейка в окружении нулей — неоднозначно.
Нулевая ячейка пиком быть не может.

Python-дубля в `composition.py` нет сознательно: офлайн-путь (`run_pipeline`)
пики не использует, а дублирование логики в двух языках без потребителя —
источник рассинхрона.

**Изменённые файлы:**

- `apps/api/schemas.py` — `RecomputeResult.peak_threshold`
- `apps/api/main.py` — `_AGG_SQL` дополнен `percentile_cont`, `recompute()`
  считает и возвращает `peak_threshold`
- `apps/web/src/App.jsx` — слой `dist-peak-outline` (чёрный контур на
  ячейках выше порога)

## 7. Линии концентрации

Если пиков больше одного — соединить их линиями.

**Почему MST (минимальное остовное дерево), а не "все со всеми":** при K
пиках MST — это `K-1` линия без циклов и минимальной суммарной длиной,
вместо `K*(K-1)/2` связей одинаковой "силы" на любом расстоянии.
Однозначно определяется координатами точек, без параметров для подбора.

**Пики-точки:** смежные ячейки-пики кластеризуются через
`ST_ClusterDBSCAN(eps=1)` (физическое касание полигонов ячеек, не
произвольный порог расстояния); оставляются кластеры по правилу Парето —
сильнейшие по суммарной массе, вместе накрывающие `peak_mass_share`
(дефолт 0.90) массы пиковых ячеек. Число пиков адаптируется к структуре
концентрации (моноцентричная Якутия — 3, полицентричное Подмосковье — ~60
на worldpop) и не зависит от масштаба карты: при переходе регион->страна
отбор везде идёт по одной доле массы — общий "уровень моря" без перекоса
высот пиков (фиксированный топ-K такой перекос давал бы);
представитель кластера — ячейка с
максимальным значением, не геометрический центроид (на невыпуклой форме
кластера центроид может попасть в ячейку с низким значением).

**API:** `GET /api/concentration-structure?region_id=&indicator=&weights=&peak_frac=`
— SQL находит и кластеризует пики, Python (`scipy.sparse.csgraph.
minimum_spanning_tree`) строит MST. Возвращает GeoJSON
`FeatureCollection` (Point-пики + LineString-рёбра) — реальные фичи, не
векторные тайлы (фич мало, тайлы не оправданы).

**Фронт:** точки и линии рендерятся отдельным GeoJSON-слоем поверх карты,
по клику на пик — попап со значением.

## 8. Модель затухания

Убывающая модель затухания от пиков/линий, коэффициент — подобрать
эмпирически (черновик ТЗ предлагал "2× на 1 км" — это эквивалент σ≈1.44 км,
слишком сильное затухание, см. обоснование ниже).

**Почему σ=10 км как отправная точка, а не "2× на 1 км":** при σ≈1.44 км
вклад падает ниже 5% уже за 4-5 км — на сетке 1×1 км это значит, что даже
соседняя ячейка получает сильно урезанный сигнал. Во всех остальных масках
проекта с той же семантикой ("затухание от точки экономической
активности") σ лежит в диапазоне 8-30 км (`distance_to_city`=10,
`railway`/`power`=8-10, `distance_to_center`=30). Пик суммарного слоя — по
построению точка устойчивой концентрации, ближе по значимости к городу,
чем к отдельному объекту инфраструктуры — поэтому σ=10 км по аналогии с
`distance_to_city`. **Это не финальное значение** — параметр открыт наружу
специально для подбора и визуальной проверки, как и просит ТЗ.

**SQL/живая отрисовка:** пики+линии считаются один раз на фронте (вместе с
`/api/recompute`), НЕ пересчитываются на каждый тайл карты — иначе MST на
каждый z/x/y был бы неприемлемо дорог. Фронт передаёт уже готовые точки и
линии в URL тайла `tile_composition`, SQL-функция только считает
расстояние (дёшево: единицы-десятки пиков) и подмешивает `exp(-d/σ)` в
цвет.

**Новая миграция:** `deploy/helm/spatial-masks/files/migrations/
0007_tile_composition_decay.sql` — `CREATE OR REPLACE FUNCTION
tile_composition` с доп. параметрами `peaks`/`lines`/`sigma_km`/`beta`/
`vmax`. Обратная совместимость: `beta` по умолчанию 0 (эффект выключен),
старые вызовы без новых параметров работают как раньше.

**Фронт:** секция "Затухание от пиков (ТЗ п.6)" — чекбокс + два живых
слайдера (σ 1-30 км, вклад в цвет 0-1), выключено по умолчанию.

## 9. Нормализация и Масштаб сравнения (Территория / Россия)

**Нормализация значения ячейки** (уже была реализована в `tile_composition`,
зафиксирована как контракт):

```
cell_abs = (raw_weight ячейки / Σ raw_weight по региону) × показатель_региона
```

**Селектор "Масштаб сравнения":**

- **Территория** — цветовая шкала растянута до максимума выбранной
  территории: видна её внутренняя структура (как было).
- **Россия** — шкала фиксирована на показатель: `color = scale(value /
  global_p99)`, где `global_p99` — 99-й перцентиль `cell_abs` по **всем**
  загруженным регионам при текущих весах (`GET /api/global-scale`). p99, а
  не max — чтобы шкалу не определяла одна аномальная ячейка. Одинаковый
  цвет = одинаковое абсолютное значение в одних единицах; при смене
  территории шкала не меняется. Значения выше p99 прижимаются к верхнему
  цвету.

**Доля России.** Для национального режима нельзя умножать вес ячейки сразу
на национальный показатель — веса нормированы внутри региона и между
регионами несопоставимы. Правильно: сначала `cell_abs` через региональный
показатель, затем `cell_national_share = cell_abs / national_total`.
`national_total` — строка `object_level='Страна'` того же parquet (та же
единица измерения по построению), хранится в `indicator.national_total`
(миграция `0008_indicator_national_total.sql`), заполняется ETL.

**Тултип ховера** показывает все три величины сразу:
`Абсолютно: 3,93 млрд руб.` / `Доля территории: 0,074%` /
`Доля России: 0,0053%`.

**Парето-пики остались территориальными** — выбранная территория сама
отбирает кластеры, накрывающие 90% её массы; селектор меняет только окраску
и подписи.

**Попутно исправлен баг данных:** `regional_value_lookup` в ETL брал первую
строку parquet без фильтра по `subsection` — для `Y477090007` (четыре
подраздела ОКВЭД) в БД попадало значение "Водоснабжение..." вместо
"Обрабатывающие производства" (Москва: 195 вместо 5275 **млрд** руб.;
единица тоже исправлена — млрд, не млн). Добавлен `indicators.<code>.
subsection` в `etl/config.yaml`; уже загруженные данные чинит миграция
`0009_fix_y477090007_regional_values.sql` — распределения масштабируются
точным коэффициентом new_rv/old_rv (значения линейны по rv; Джини/top-10%
от масштаба не зависят). Миграции прогоняются целиком на каждом деплое,
поэтому 0009 **самоотключаема**: масштабирование срабатывает только если
сумма эталонной композиции региона равна старому ошибочному rv (допуск
1e-6), `national_total` заполняется только при NULL, единица правится
только с заведомо старого значения — повторные прогоны и данные будущих
ETL-прогонов не затрагиваются.

**`science_mask` — 11-я маска.** Точки OSM: `amenity=research_institute|university|college`,
`office=research`, `building=university`; вес `norm(exp(-d/15км))` до ближайшей
точки, поэтому плотность объектов внутри кампуса на вес не влияет — только его
наличие. σ = 15 км: больше, чем у `distance_to_city` (научная агломерация — город
с вузом и пригороды), меньше, чем у `distance_to_center` (сигнал должен различать
наукоград и соседний райцентр). Считается тем же
`scripts/compute_masks_overpass --only science`, что и четыре маски НСО.

Зачем она нужна: до неё научно-технологические показатели опирались на
`distance_to_center` + `worldpop`, то есть на «где центр региона» и «где живут
люди». Для патентов и НИОКР это заведомо неверный прокси — наука сидит в
конкретных точках. Разброс маски по регионам это и показывает: медиана веса
0,27 в Подмосковье (вузы почти везде), 0,16 в Краснодарском крае, 0,001 в НСО и
0,0001 в центральной Якутии — то есть в Сибири и на Севере наука сосредоточена в
Академгородке и Якутске, а не размазана по населению.

В набор масок ИКГС (`MASK_ORDER`) она НЕ входит: у индекс-ячеек нет её столбца
(они считаются отдельно в `ingest_index`), да и яркость индекса качества
городской среды от близости к НИИ не зависит.

**Попутно исправлен второй баг данных.** Росстат кодирует отсутствие значения не
пропуском строки, а сентинелом в самом значении: `-77777777` («данные не
публикуются в целях конфиденциальности», ст. 4 п. 5 / ст. 9 п. 1 282-ФЗ) и
`-99999999` — в массиве таких строк ~149 тыс. Попав в `regional_value`, сентинел
ломает не один слой, а весь регион: min-max нормировка §4.1 растягивается на
−7,8·10⁷, и все остальные ячейки сжимаются в ноль. Нашлось на `Y477110352` в
Якутии. `regional_value_lookup` теперь фильтрует сентинелы и по §4.2 методики
берёт последний доступный предыдущий период (Якутия: 2021 г.) с печатью
примечания в лог; плюс `assert` в ингесте — сентинел лучше уронить прогон, чем
залить в БД.

### Форма 2-наука по НСО: скрапер

`scripts/scrape_nauka_nso.py` забирает публикации Новосибирскстата из раздела
[«Наука и инновации»](https://54.rosstat.gov.ru/folder/32625) — это разрезы формы
№ 2-наука («Сведения о выполнении научных исследований и разработок», ОКУД
0604011) по Новосибирской области за 2008–2024 гг.

Сами отчёты респондентов не публикуются (ст. 4 п. 5 / ст. 9 п. 1 282-ФЗ,
конфиденциальность первичных данных), поэтому на уровне организаций скрапить
нечего — сводов территориального органа это потолок. Зато в сводах есть то, чего
нет в росстатовском parquet: **внутренние затраты по источникам финансирования**
со строкой «средства бюджетов всех уровней» и разбивкой на федеральный бюджет /
бюджеты субъектов РФ — то есть пункт ТЗ про объём бюджетной поддержки, который
иначе закрывался только суррогатом (`Y477110102`, все затраты на инновации).
Плюс затраты по видам работ (фундаментальные / прикладные / разработки), по
видам затрат, по приоритетным направлениям, численность персонала по категориям
и по учёным степеням, число организаций.

Выгрузка: 703 значения, 8 таблиц, `data/raw/nauka_nso/nauka_nso_long.csv`
(source, table, unit, section, label, indent, year, value) + `raw/` с
исходниками, `wide/` с прямоугольными дампами одногодичных таблиц и
`manifest.csv` (url, размер, sha256).

Три вещи, на которых парсер спотыкался и которые закрыты проверками
(`--selftest`, без сети):

- **TLS.** `rosstat.gov.ru` отдаёт сертификат УЦ Минцифры, которого нет ни в
  одном стандартном trust store — без `verify=False` падает любой запрос. Это
  анонимные GET публичных файлов, так что понижение проверки безопасно; если
  корневой сертификат установлен, есть `--ca-bundle`.
- **Иерархия задана отступами ячеек, а не текстом.** «средства организаций
  госсектора» стоит на том же отступе, что «средства бюджетов всех уровней»,
  но идёт ПОСЛЕ вложенного «в том числе:» — без чтения `alignment.indent` он
  выглядел подпунктом, и сумма по разрезу двоилась.
- **На одном листе несколько таблиц.** В файле по численности работников их
  две («по категориям персонала» и «имеющих учёную степень»), у каждой своя
  строка с годами. Определять шапку по «трём числам вида 19xx/20xx» нельзя:
  численность техников — это 1986, 2056, 2047 человек, такая строка данных сама
  выглядела шапкой. Признаки шапки берём от файла: пустая ячейка в столбце
  подписей и строго возрастающие годы.

Контроль на реальной выгрузке: категории персонала складываются в «Всего» точно
(2008: 21597, 2016: 21843, 2024: 20738), ни одна подпись строки не является
годом.

## 11. Сквозная демонстрация: `scripts/demo_e2e.sh`

Воспроизводимый прогон всего пути — parquet Росстата → PostGIS → API → тайл
карты — на двух показателях: `Y477110196` (коэффициент естественного прироста
на 1000 чел.) и `Y477110197` (коэффициент миграционного прироста на 10000 чел.).

```
./scripts/demo_e2e.sh            # moscow по умолчанию
./scripts/demo_e2e.sh yakutia_center
```

Нужны только docker compose, curl, jq, python3 — сеть не требуется, все входные
данные (parquet, сетки, csv-масок) уже лежат в `data/`. Шесть шагов, каждый
проверяется, любой сбой роняет скрипт:

1. **Сырое значение** — читается той же функцией `regional_value_lookup`, что и
   в ингесте (фильтр сентинелов −77777777/−99999999, откат на последний
   доступный год по §4.2), плюс национальный итог (`object_level='Страна'`).
2. **Платформа** — `docker compose up -d db tiles api web`, ожидание `/health`.
3. **Ингест** — `etl.ingest --region <slug> --indicator Y477110196 --indicator
   Y477110197`. Флаг `--indicator` добавлен для точечных прогонов: справочник
   `indicator` грузится целиком (фронт берёт из него названия), а сетка, 11 масок
   и композиции считаются только по перечисленным кодам, а не по всем 25.
4. **БД** — `regional_value` на композиции (0012) и `national_total` (0008).
5. **API** — `/api/regions` → `/api/indicators` → `/api/default-weights` →
   `POST /api/recompute` → тайл `tile_composition` по центру региона (проверяется,
   что MVT непустой) → `/api/concentration-structure` (пики + рёбра MST).
6. **Результирующий слой** — `/api/composite`: оба кода входят в свод со своими
   векторами весов масок (`composite_config`), проверяются `skipped` и
   `missing_masks`.

Прогон на МО (141 967 ячеек): 2 показателя, 11 масок, ~7 минут.

### Что демонстрация выявила и что исправлено: удельные показатели

Оба кода — **коэффициенты** (ставки «на 1000/10000 человек»), а не объёмы, и
`Y477110196` в трёх пилотных регионах из четырёх **отрицателен** (МО −2,5,
Краснодар −3,2, НСО −3,5; Якутия +3,4). Прежний инвариант платформы
`Σ по ячейкам = региональное значение` для ставки неверен при любом знаке:
сумма коэффициентов рождаемости по ячейкам не равна коэффициенту по региону, а
ячейке достаётся величина, которая не является ни ставкой, ни числом людей (для
МО прежний код разносил −2,5 так, что «сумма» по ячейкам давала −103 985).
Отрицательное значение просто сделало ошибку видимой:

- Джини сохранялся отрицательным (−0,515 против 0,515 у объёмного показателя с
  тем же рельефом) — вне области определения метрики, а `top10_share` брал
  наименее концентрированные ячейки (0,003 вместо 0,326);
- `peak_threshold = p95 · rv/total` тоже отрицателен, а фронт фильтрует
  `value >= peak_threshold` — при `rv < 0` неравенство переворачивается и
  «пиком» становились **95 %** ячеек (134 868 из 141 967 в МО);
- шкала цвета на отрицательном `value_max` откатывалась на `vmax = 1` и красила
  регион одним нижним цветом.

**Исправление.** У ставки сохраняется взвешенное **среднее**, а не сумма:

```
объёмный: value_i = rv · w_i / Σw          =>  Σ value_i = rv
ставка:   rate_i  = rv · w_i / w̄,          =>  Σ(base_i·rate_i)/Σbase_i = rv
          w̄ = Σ(base_j·w_j) / Σbase_j
```

`base` — знаменатель самой ставки: население (на 1000/10000 чел., кв.м на
жителя) или площадь (плотность дорог). Отличие ровно в знаменателе нормировки,
поэтому `tile_composition` менять не пришлось — API передаёт `w̄` тем же
параметром `total`.

- **Миграция** `0013_indicator_rate_base.sql` — колонка `indicator.rate_base`
  (`population` | `area` | NULL = объёмный), разметка семи уже загруженных
  удельных показателей, замена сентинела `unit: 'ND'` на настоящие подписи и
  удаление сохранённых метрик ставок, считанных по знаковым значениям. Живой
  путь считает всё от `mask_cell_value` и `composition.regional_value`, поэтому
  карта и пики становятся корректными сразу после миграции, до прогона ETL.
- **Расчёт:** `composition.distribute_rate` / `check_mean_preservation`,
  `pipeline.run_pipeline(rate_base=…)`. Инварианты проверяются без БД и сети:
  `python -m src.masks.composition`.
- **Метрики:** Джини и `top10_share` считаются по рельефу масок, а не по
  значениям. Обе — отношения, то есть инвариантны к положительному масштабу: у
  объёмного показателя это ровно те же числа, что раньше, а у ставки они
  остаются в своей области определения. `sum_error` у ставок заменён на
  `mean_error` — чтобы одно имя метрики не значило разное у разных показателей.
- **API:** `/api/recompute` считает знаменатель по типу показателя, возвращает
  `value_min` и `rate_base`, а порог пиков берёт `percentile_cont(0.05)` вместо
  `0.95`, когда множитель `rv/scale` отрицателен (иначе «верхние 5 % по
  значению» — это нижние 5 % по весу). `/api/global-scale` использует тот же
  знаменатель, а базой для ставки отдаёт российскую ставку, не «итог/ячейку».
- **Фронт:** база LQ-шкалы для ставки — сама региональная (или российская)
  ставка, а стопы задаются в кратных базы (`["/", ["get","value"], base]`) —
  при отрицательной базе стопы `base·m` шли бы по убыванию, и MapLibre отверг
  бы выражение. Тултип для ставки показывает ставку ячейки рядом со ставкой
  региона и РФ, а не «долю территории/России» — доли от ставки не считаются.

Проверено на прогоне (МО, `Y477110196`): взвешенное по населению среднее по
141 967 ячейкам = **−2,5000000000** (ровно региональный коэффициент Росстата),
диапазон ячеек −6,504 … −0,0005 на 1000 чел., Джини 0,504 (положительный),
ячеек выше порога пиков **5,0 %**.

Что осознанно НЕ менялось: пики и линии концентрации
(`/api/concentration-structure`) считаются по сырым весам масок — это структура
рельефа, она от знака показателя не зависит и была корректна. Результирующий
слой `/api/composite` нормирует слои min-max по §4.1, региональное значение в
него не входит, поэтому ставки в своде и раньше считались правильно.
